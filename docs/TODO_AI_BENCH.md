# 待做：AI 自建多轮劳动争议评测集（尽量不靠人工）

> 目标：30–50 个多轮劳动争议咨询案例，覆盖 12 类请求权，每个案例带
> 隐藏事实、金标准要件/金额/时效、一次事实更正；**人工只做 10–20% 抽查**，
> 不手写 gold、不逐条打分。

---

## 1. 为什么可以交给 AI

一个评测案例需要四样东西：

| 组成 | 能不能由 AI 生成 | 关键约束 |
|---|---|---|
| 案情与隐藏事实 | 可以 | 必须满足要件分支，不能自相矛盾 |
| 金标准结论/金额/时效 | **不靠生成，靠符号层计算** | 用项目自己的规则层当 oracle，生成器不能自己写 gold |
| 当事人开场白/回答风格 | 可以 | 要口语、模糊、可能带错误法律理解 |
| 更正脚本 | 可以 | 只改一个事实，且新值要能改变结论 |

关键设计：**生成器负责“造题”，符号层负责“判卷”，另一个模型负责“审题”**。
三者分离，避免“自己出题自己给答案”。

## 2. 流水线

```text
法条/实务提示/公开案例
        │
        ├─ ① 种子采样：请求权、要件分支、地区、金额档位
        │
        ├─ ② 生成器 LLM：案情 + 隐藏事实 + 开场白 + 更正
        │
        ├─ ③ 符号 oracle：把隐藏事实代入 rules.analyse_many
        │       └─ 算不出确定结论 → 丢弃/重生成
        │
        ├─ ④ 一致性过滤：日期顺序、枚举合法、分支覆盖、无答案泄漏
        │
        ├─ ⑤ 审题模型：另一个 LLM 判断“像不像真实咨询/法律上是否自洽”
        │       └─ 不通过 → 重生成或标人工
        │
        ├─ ⑥ 脚本化当事人：只回答被问到的 key，其余“不清楚”
        │
        └─ ⑦ 人工抽查 10–20%：只看“是否真实、是否有歧义”，不改 gold
```

### ① 种子采样

- 请求权：12 类，每类 2–4 个；
- 要件分支：每个 `critical_if` 至少覆盖一次（严重违纪/不胜任/客观情况/协商一致/被迫解除……）；
- 金额档位：低于/等于/高于当地最低工资 12 倍（一裁终局边界）；
- 日期档位：时效内/临界/已过；2022-05-01 前后（侵权城乡标准）；2025-09-01 前后（解释二）；
- 事实组合：单请求权 / 多请求权（辞退+欠薪、工伤+交通）。

### ② 生成器提示词约束

给 LLM 的 schema 包括：

- 允许的 claim id、字段、枚举值；
- 必须填的隐藏事实 key；
- 不能出现的矛盾（如 `dismiss_date < start_date`）；
- 开场白不能直接说出所有隐藏事实；
- 更正只能改一个事实，且新旧值都要合法。

### ③ 符号 oracle

```python
facts = case["hidden"]
analysis = rules.analyse_many(case["claims"], facts, today)
gold = {
    "illegal": analysis.metadata.get("illegal"),
    "amount": analysis.metadata.get("compensation", {}).get("amount"),
    "limitation_deadline": analysis.metadata.get("limitation", {}).get("deadline"),
    "interp": analysis.metadata.get("interp"),
}
```

- 如果 `compensation.ok == False` 或 `limitation.ok == False`，说明事实不足以算出确定结论 → 丢弃；
- 金额/时效 gold 来自规则层，不是 LLM 写的；
- 规则层本身有简化（未接入当地社平工资），所以 gold 只在这些假设下成立，案例里要写清楚。

### ④ 一致性过滤（代码，不用模型）

- 日期：入职 < 解除；事故日 < 今天；工伤认定在受伤后；
- 枚举：必须在该字段 `options` 内；
- 分支：至少一个 `critical_if` 被触发；
- 泄漏：开场白不能包含 gold 金额/“违法”等结论词；
- 更正：`new != old`，且用新值重跑 oracle 后结论确实变化；
- 去重：按 claim + 关键事实组合做哈希。

### ⑤ 审题模型

另一个 LLM 只看案情，回答：

- 这是不是一个人会问的问题？
- 事实有没有明显法律矛盾？
- 开场白有没有“AI 味”或直接报答案？
- 如果它来问，最想问的前三个问题是什么？

不通过就重生成；连续失败标“人工复核”。

### ⑥ 脚本化当事人

复用 `eval/protocol.py`：

- 只回答被问到的 key；
- 未问到的隐藏事实不主动说；
- 可按 persona 加“记不清/情绪化/答非所问”；
- 更正脚本在第一次备忘录后注入。

### ⑦ 人工抽查

只抽 10–20%，回答三个问题：

- 这个案情是否可信？
- gold 的假设是否写清楚？
- 有没有明显法律错误？

**不改 gold、不逐条打分**；发现系统性问题才回到生成器/规则层。

## 3. 验收标准

- 30–50 个案例，12 类请求权每类 ≥2；
- 每个 `critical_if` 分支至少 1 个案例；
- 多请求权 ≥8 个；
- 更正案例 ≥10 个；
- 每个案例的 gold 可由 `rules.analyse_many` 复现（同一版本、同一 today）；
- 人工抽查通过率 ≥90%；
- 指标：要件覆盖率、追问召回、过早结论率、金额/时效准确率、引用可核验率、旧结论残留、平均问题数。

---

## 4. 风险与缓解

| 风险 | 缓解 |
|---|---|
| LLM 生成的案情分布偏移 | 用真实法条/实务提示做种子；覆盖矩阵约束；人工抽查 |
| gold 泄漏进开场白 | 关键词/金额/结论词过滤；审题模型检查 |
| 规则层简化被当成“法律正确” | 案例卡写清假设；报告只声称“管线一致性” |
| 生成器与 oracle 同源偏差 | 规则层由人审过的法条驱动；另建一个独立计算脚本做交叉校验 |
| 案例太“配合” | persona：模糊、回避、情绪化、前后不一致 |
| 成本 | 小模型生成 + 规则 oracle + 抽样审题；30–50 个案例成本可控 |
