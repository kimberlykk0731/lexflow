# 评测设计：我们到底测了什么，没测什么

> 结论先行：这套评测能支持“追问门控与版本化记忆改善了咨询流程的一致性”，**不能**支持“我们的法律结论比别的模型更正确”。报告里必须区分这两句话。

---

## 1. 为什么不用现成 benchmark 当主实验

2025–2026 年已经有一批质量很高的法律 agent benchmark：

| Benchmark | 覆盖 | 为什么没直接拿来当主实验 |
|---|---|---|
| [DLawBench](https://arxiv.org/abs/2606.13931)（2026） | 461 个中/美真实案件改写，四种当事人人格，Elicitation / Resolution / Fidelity | 最接近我们的设定；但它的 lawyer 是通用对话策略，我们的要件 schema 只覆盖劳动与侵权两个案由，直接跑会把大部分案例分错类 |
| [LeCoDe](https://aclanthology.org/2026.acl-long.1667/)（ACL 2026） | 3,696 段真实咨询，关键事实与重要性标注，追问召回 / NDCG | 数据需签署协议申请，课程周期内不确定能拿到 |
| [LegalAgentBench](https://aclanthology.org/2025.acl-long.116/)（ACL 2025） | 300 任务、37 工具、中文法律环境 | 依赖远程 law_api，且偏检索/多跳查询，不评“该不该先问” |
| [LexAgentHallu](https://aclanthology.org/2026.emnlp-main.2121/)（EMNLP 2026） | 3,414 条轨迹级幻觉标注 | 需要专家标注体系，课程项目无法复现 |

所以本项目**不声称构造新 benchmark**，也不声称在公开榜单上超过谁。我们只做一件小而清楚的事：在**两个案由**上，用**受控脚本**测三个机制。DLawBench / LeCoDe 作为设计参照与外部效度讨论，不作为成绩来源。

## 2. 受控咨询协议

### 2.1 案例构造

`data/eval/scripted_cases.json`，12 个案例：

- 7 个劳动争议解除（L01–L07），覆盖：未公示、已公示、不胜任未培训、不胜任合规、协商一致、时效已过、更正解除日期。
- 5 个交通事故人身损害（T01–T05），覆盖：2022-05-01 前后、2020 年（适用 2003 年解释）、2022-03（适用 2020 年解释）、更正事故日期跨版本。

### 2.1.1 这些案例是真实的吗

不是真实判决，也不是真实当事人。12 个案例是**教学 fixture**：事实、姓名、日期都是构造的，但**法条原文是真的**（逐条来自公开整理仓库，带生效期），**金标准是作者按法条手算的**，不是系统生成。

| 真的部分 | 构造的部分 |
|---|---|
| 劳动合同法、司法解释、调解仲裁法、民法典、侵权责任法、人身损害赔偿解释的条文与生效期 | 具体当事人、日期、金额、对话 |
| 解除合法性、时效、补偿/赔偿、城乡标准的法律规则 | 12 个案例的事实组合与更正脚本 |
| 金额/期限的计算方法 | 当地社平工资、奖金口径、伤残系数、医疗票据（未接入） |

如果老师问，主动说“合成案例 + 真实法条 + 手算 gold”，比暗示是真实案件安全。真实案件不应由课程 demo 虚构案号或裁判结果。

每个案例包含：

```json
{
  "opening": "当事人第一句话（模糊、口语、可能含错误法律理解）",
  "hidden": {"dismiss_date": "2026年3月15日", "...": "..."},
  "correction": {"text": "更正……", "fact": "dismiss_date", "old": "...", "new": "..."},
  "gold": {"illegal": true, "amount": 150000, "limitation_deadline": "2027-03-15",
           "critical": ["dismiss_date", "..."]}
}
```

- `hidden` 是当事人“知道但不会主动全说”的事实。脚本化当事人**只回答被问到的字段**，其余回答“不清楚”。
- `gold` 由作者依据法条手工计算（不是系统规则生成）。`critical` 是该案由下会改变结论的要件事实。
- `correction` 在**第一次备忘录之后**注入，模拟“当事人回去翻了材料，发现记错了”。

### 2.2 四个配置

| 配置 | 追问 | 检索/规则 | 核验/修复 | 更正后重算 |
|---|---|---|---|---|
| `answer_first` | ✗ | ✓ | ✗ | ✓ |
| `gate_only` | ✓ | ✓ | ✗ | ✓ |
| `full` | ✓ | ✓ | ✓ | ✓ |
| `full_no_revision` | ✓ | ✓ | ✓ | ✗（复用旧分析） |

`full_no_revision` 不是“另一个模型”，而是同一系统的消融：它保留更新后的事实表，却复用更正前的分析结果——这正是很多“有记忆但没有版本”的 agent 会出现的缺陷。

### 2.3 指标

| 指标 | 定义 | 说明 |
|---|---|---|
| 事实覆盖率 | 备忘录生成时，`gold.critical` 中已取得的比例 | 衡量“信息够不够” |
| 追问召回 | 开场未主动提供的关键事实中，被系统主动问到的比例 | 分母排除开场已说的事实，避免惩罚“当事人主动说” |
| 提问数 | 去重后的追问字段数 | 效率 |
| 过早结论率 | 覆盖率 < 1 就出备忘录的比例 | “不懂装懂” |
| 引用可核验率 | 结论引用通过“存在/案发日有效/引文对得上/依赖事实未过期”的比例 | 机械核验，不等于论证正确 |
| 违法认定一致率 | `metadata.illegal` 与金标准一致 | 规则一致性 |
| 金额一致率 | 计算金额与手算金标准误差 ≤1 元 | 算术一致性 |
| 时效一致率 | 时效届满日与金标准一致 | 时间效力 |
| 版本选择一致率 | 侵权司法解释版本与金标准一致 | 时间效力 |
| 旧结论残留率 | 更正后最终备忘录仍使用旧期限/旧版本的比例 | 只在 2 个含更正的案例上算 |

### 2.4 当前结果（DeepSeek API）

命令：`PYTHONPATH=src python3 eval/run_evals.py --llm api --out runs/api`

| 条件 | 覆盖率 | 追问召回 | 提问数 | 过早结论 | 引用核验 | 违法 | 金额 | 时效 | 版本 | 旧结论残留 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| answer_first | 57.5% | 41.7% | 0.0 | 58.3% | 83.3% | 85.7% | 0% | 50% | 100% | — |
| gate_only | 100% | 100% | 4.4 | 0% | 100% | 100% | 100% | 100% | 100% | 0% |
| full | 100% | 100% | 4.4 | 0% | 100% | 100% | 100% | 100% | 100% | 0% |
| full_no_revision | 100% | 100% | 4.4 | 0% | 92.2% | 100% | 85.7% | 83.3% | 80% | 100% |

全部 4 个条件 × 12 案例共消耗 149k 输入 + 11k 输出 tokens，按 DeepSeek 2026 官方价估算约 **0.17 元**。mock 结果见 `runs/mock/`，只用于验证无 API 时链路可跑。

**怎么读这张表：**

1. `answer_first` 的低覆盖率与高过早结论率，是“搜索助手”基线的核心问题：它不会停下来问。
2. `gate_only` 与 `full` 的差距为 0，是因为规则层产出的引用本来就是有效的——核验器在正常运行中抓不到东西。它的价值必须用注入测试衡量（下节）。
3. `full_no_revision` 的旧结论残留 100%，说明“有记忆”不等于“会更新”。
4. 违法/金额/时效/版本的 100% 是**同源**结果（规则层与金标准都由作者按法条编码），不能当作“法律能力”宣称。

### 2.5 统计口径

n=12，样本小，不做显著性检验；报告逐案例表（`runs/eval_cases.csv`），只做描述性比较。若要写“显著”，至少需要把案例扩到 50+ 并做配对 bootstrap，这在课程周期内不现实，报告中明确写“exploratory”。

## 3. 核验器注入测试

`eval/verify_probe.py`：对每个干净分析注入 5 类缺陷，检查核验器是否报出对应 code。

| 缺陷 | 注入方式 | 检出 |
|---|---|---|
| `UNKNOWN_SOURCE` | 把引用改成不存在的第 999 条 | 12/12 |
| `VERSION_NOT_IN_FORCE` | 把引用改成案发日尚未生效的版本 | 12/12 |
| `QUOTE_MISMATCH` | 塞入原文中不存在的引文 | 12/12 |
| `SUPERSEDED_FACT` | 把依赖事实的 revision 调到分析之后 | 12/12 |
| `UNVERIFIED_NUMBER` | 把赔偿金额改成 999,999 | 7/7 |

干净分析误报：12 个案例 0 条。

**局限**：这是“核验器对注入错误的敏感度”，不是“核验器能发现所有法律错误”。它抓不到：法条选错但版本有效、论证跳跃、类案不可比、事实上真实但法律上不相关。

## 4. 缓存实验

`eval/cache_bench.py`：

| 场景 | 执行工具 | 缓存命中 |
|---|---:|---:|
| 开缓存，无新事实重放 | 0 | 18 |
| 关缓存，同样重放 | 18 | 0 |
| 更正解除日期后 | 8 | 10 |

更正后只有 1 条依赖 `dismiss_date` 的缓存被失效，公共法条检索与条文读取继续命中。这说明缓存粒度是“事实依赖”，不是“整会话清空”。

**不要过度解读**：命中数不等于 token 节省；工具是本地 BM25，耗时不能代表真实检索延迟。

## 5. 人工盲审（必须做，成本约 2 小时）

从 `full` 条件随机抽 10 份备忘录（劳动 6、侵权 4），隐去系统名，让两名互不沟通的评审按下面 5 项 0/1 打分：

| 维度 | 通过标准 |
|---|---|
| 结论可追溯 | 每条结论都能指到具体法条/计算 |
| 事实与假设分离 | 明确区分“当事人说”“材料支持”“我们的假设” |
| 缺口诚实 | 不知道的事实没有被编造，且给出补材建议 |
| 时效与版本 | 适用的法条版本与案发日一致 |
| 可读性 | 非法律人士能看懂结论与下一步 |

记录两人的一致率（简单 percent agreement 即可）与分歧点。报告里写“10 份中 X 份全项通过，分歧 2 处，经讨论后……”。这比再跑一个 LLM judge 更有说服力，也符合课程规模。

模板见 `docs/memo_review_sheet.md`。

## 6. 效度威胁（写报告时主动承认）

| 威胁 | 表现 | 缓解 |
|---|---|---|
| 构念效度 | “覆盖率/引用核验”不等于“法律服务质量” | 明确指标边界；加人工盲审 |
| 内部效度 | 金标准与规则层同源，结论一致性被高估 | 报告只把流程指标当主结果；金标准逐条附法条依据，供第三方复核 |
| 外部效度 | 只有两个案由、12 个案例、脚本化当事人 | 明确不外推；讨论 DLawBench/LeCoDe 的差异 |
| 生态效度 | 当事人太配合，不会情绪化/隐瞒 | 下一阶段用 DLawBench 四种人格；当前作为局限 |
| 数据效度 | 法条文本来自二手整理仓库 | 记录来源与版本；正式引用核对 flk.npc.gov.cn |
| 检查盲区 | 案发日缺失时，版本检查会跳过；核验器抓不到论证错误 | 报告中明说；案发日缺失时结论标“时效/版本未核验” |
| 评测者偏差 | 作者既写系统又写金标准 | 盲审 + 公开 gold 与计算过程 |

## 7. 如果老师问“这算不算 benchmark”

标准回答：

> 不算。我们没有提出新的评测基准，也没有声称覆盖法律任务的全貌。我们提出的是一套**受控行为测试**：用隐藏事实与更正注入，测量 agent 在信息不完整、事实被修订时的行为。它的价值在于可复现、可解释，而不是规模。公开 benchmark（DLawBench、LeCoDe）在我们的相关工作与局限部分，作为外部效度参照。
