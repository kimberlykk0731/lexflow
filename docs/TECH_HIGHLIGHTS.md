# 技术点：哪些是“高级”的，哪些只是工程

> 先说结论：这个项目的主体不是“训练了一个更强的法律模型”，而是**神经符号系统 + 主动问询 + 可核验检索**。
> 如果没有把这几个机制显式做出来、测出来，它看起来就只是一个“会问问题的 prompt 壳”。
> 下面按“可展示、可度量、可复现”三个标准列。

---

## 1. 神经符号分解（neuro-symbolic decomposition）

- LLM 只做两件低风险的事：**事实抽取**（带 JSON 约束、枚举校验）和**措辞改写**（不许新增事实/法条）。
- 是否追问、走哪个要件分支、适用哪条法、金额怎么算，全部由**符号层**（要件树 + 规则 + 计算器）决定。
- 好处：引用和数字可核验、可复现；模型幻觉不会直接变成结论。
- 代价：规则层是作者编码的，覆盖有限；这是“可审计”换“泛化”的取舍。

**可展示**：每次回答都带“要件链”，能看出哪条结论来自哪条规则。

---

## 2. 主动问询：价值信息（VOI）排序

静态 `priority` 只能回答“这个事实法律上重要”；不能回答“现在问它会不会改变结论”。

`src/lexflow/voi.py` 做的是一个轻量、可解释的 **value-of-information**：

1. 取当前要件树的前沿问题（frontier）；
2. 对每个问题枚举可能的回答（枚举项、若干金额/日期档位）；
3. 把每个假设回答代入**确定性规则层**，得到不同的结果签名（如“违法/合法”“2N/N/0”“时效过/没过”）；
4. 能区分的结果种类越多，VOI 越高；完全不能改变结论的问题降权。

例子：

```text
问题：公司有没有公示员工手册？
信息价值：回答后可在 2 种可能结果之间区分（其余事实不变）
```

这不是 full Bayesian belief update，而是**model-based active interrogation**：
用一个可执行的符号模型当“世界模型”，用结果集合的缩小量近似信息增益。
优点是可解释、无需训练、和规则层一致；缺点是只做单变量近似，不建模问题之间的联合信息。

**可度量**：12 个脚本案例上，开/关 VOI 的平均提问数都是 5.2，覆盖率/金额/时效都保持 100%。
这说明 VOI 在当前案例上主要改变**排序和解释**，没有降低问题数；它的 early-stop 只在
“剩余问题都不改变结论”时触发。要证明效率收益，需要专门构造 must-ask 已满足、
剩余全是 outcome-neutral 的场景，这是下一步实验。

---

## 3. 时间效力感知的检索（temporal RAG）

法条不是普通文档：同一“第47条”在不同时间有不同版本。

- 语料每条记录带 `valid_from / valid_to`；
- 检索时先按案发日过滤版本，再做 BM25；
- 引用核验会检查“这条法在案发日是否有效”，失效则报 `VERSION_NOT_IN_FORCE` 并尝试替换为正确版本。

这是 RAG 里比较容易被忽略的一层：**retrieval 的时间约束**。
多数法律 RAG 只做“相关”，不做“当时有效”。

---

## 4. 实务知识库的 chunk 级 RAG

`data/knowledge/practice_notes.json` 里的法院/人社提示不是整篇塞进 prompt，而是：

1. 每条提示拆成 chunk（标题、每个要点、caveat）；
2. 用和法条一样的**中文字符 bigram BM25** 建索引；
3. 查询由“当前请求权 + 已识别争点”拼成；
4. 先按请求权 topic 硬过滤，再 BM25 排序，按最高分做相对阈值截断；
5. 命中 chunk 连同发布机关、日期、URL 一起进备忘录，形成**可追溯的引用**。

这是标准的 retrieve-then-generate，只是没有用向量库：
- 优点：零依赖、可复现、中文法律词表下 BM25 很强；
- 缺点：没有语义泛化（“被开除了”↔“解除”靠同义词表），没有 cross-encoder rerank；
- 升级路径：BM25 + dense embedding 混合检索 + rerank，接口已经留好（`KnowledgeBase.retrieve`）。

**可展示**：备忘录“实务提示（RAG 检索）”会显示命中的提示和 BM25 相关度。

---

## 5. 依赖感知的增量计算与缓存失效

案件事实是版本化的：每个事实有 `revision`、`source`、`superseded_by`。

- 工具调用缓存带**事实依赖列表**；
- 当事人更正一个事实，只失效依赖该事实的缓存条目；
- 分析结果记录依赖的事实；更正后重新计算，旧结论不会残留。

这不是“缓存”，而是**增量真值维护（incremental truth maintenance）**的简化版：
把“结论依赖哪些事实”显式记录下来，事实变化时做依赖传播。

**可度量**：`eval/cache_bench.py` 显示更正一个日期只失效 1 条缓存；
`full_no_revision` 条件刻意复用旧分析，旧结论残留 100%，作为对照。

---

## 6. 结论到证据的核验与有界修复

`verify.py` 不是 LLM judge，而是机械检查：

- 引用是否存在；
- 引用在案发日是否有效；
- 引文是否对得上；
- 金额是否等于计算值；
- 结论依赖的事实是否已被更正/取代。

发现缺陷后有界修复：换正确版本、删错引文、丢弃不匹配引文，再核验一次。
这相当于给生成结果加了一层**claim-to-evidence verifier**。

**可度量**：`eval/verify_probe.py` 注入 5 类缺陷，检出率 100%，干净分析 0 误报。

---

## 7. 受控的多轮咨询评测

`eval/protocol.py` 不是“找几个人打分”，而是：

- 每个案例有隐藏事实表；
- 脚本化当事人只回答被问到的问题，其余说“不清楚”；
- 第一次备忘录后注入一次事实更正；
- 指标：事实覆盖率、追问召回、过早结论率、金额/时效/版本准确率、引用可核验率、旧结论残留。

这能测出“追问是否真的把假设空间缩小了”，而不只是“回答得像不像”。

---

## 8. 没有做什么（避免过度宣称）

- 没有训练/微调法律模型；
- 没有 dense retrieval / cross-encoder rerank；
- 没有学习型问询策略（VOI 是规则模型上的枚举近似）；
- 没有真实类案检索与裁判结果预测；
- 没有校准过的概率置信度（只有“要件覆盖 + 结果集合”）。

这些都可以作为后续工作，但当前版本不应该声称“模型能力超过某某”。

---

## 9. 一句话版本

**LLM 负责“读懂人话”，符号层负责“法律结构”，VOI 负责“先问什么”，版本感知 RAG 负责“依据哪条法”，核验器负责“别胡说”。**
这五件事叠起来，才是一个可审计的法律咨询 agent，而不是一个法律 prompt。
